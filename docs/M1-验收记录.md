## 三、清理模块的设计决策

### 3.1 三种处置方式，默认用「隔离区」

| 方式 | 撤销能力 | 磁盘何时真正释放 |
| --- | --- | --- |
| **隔离区（默认）** | **100% 可撤销**（本质是一次文件移动，复用已验证的 `MoveFileUndoHandler`） | 清空隔离区时 |
| Windows 回收站 | WinKit 内不可撤销，需手动从回收站还原 | 清空回收站时 |
| 彻底删除 | 不可撤销（L3，需两道确认） | 立即 |

**为什么默认不是回收站**：规划里写的是"删的东西进回收站、可一键撤销"，但回收站的程序化还原要依赖 Shell COM 的 `InvokeVerb("还原")`，脆弱且难以可靠测试。隔离区把"撤销"退化成一次文件移动 —— 复用已有且已被 16 个测试覆盖的撤销链路，**可撤销性从"尽力而为"变成"结构性保证"**。代价是磁盘要等清空隔离区才真正释放，这一点在界面上如实写明（隔离区/回收站显示"涉及 X"，只有彻底删除才写"释放 X"）。

### 3.2 扫描器的三条安全约束

1. **只把目标目录的直接子项当候选，永远不动目标目录本身** —— "清理 `%TEMP%`" 不可能演变成"删除 `%TEMP%` 目录"。
2. **不跟随重解析点**（junction / 符号链接），避免目录循环与越界删除。
3. **跳过太新的项**（默认 1 小时），被占用的临时文件删不掉，年龄门槛先天省掉大量失败。

另外：`ScanOptions.ExcludeRoots` 必须包含 WinKit 自己的数据目录，否则清理临时目录时可能把隔离区自己搬进隔离区。

### 3.3 规则库的透明度是被测试强制的

每条规则都必须填 `Description`（这是什么）与 `Impact`（清了有什么影响），**空着测试就失败**。刻意排除的项也写明理由：

- **Prefetch**：清了会让下次启动变慢，属于反效果。
- **缩略图缓存**（`thumbcache_*.db`）：Explorer 运行时基本都处于占用状态，成功率极低，加进来只会让用户以为工具坏了。
- **Windows 更新缓存**：要停 `wuauserv` 服务，风险高，留待 L2/L3 进阶清理单独做。

## 四、本轮抓到的真实缺陷

| # | 缺陷 | 怎么发现的 |
| --- | --- | --- |
| 1 | `WmiQuery` 的重载把 `Query(wql, "Caption")` 劫持成"WQL + 命名空间"，异常被 catch 吞掉 → **所有 WMI 查询静默返回空集合**，界面全是占位符"—" | Platform 单元测试断言"不含 —" 失败 |
| 2 | `CleanupScanner.Expand` 把"环境变量展不开"与"目录不存在"混为一谈 → **把规则配置错误伪装成"正常无事发生"**，静默漏扫 | Core 测试编写者审查代码时发现 |
| 3 | `MaxItemsPerRule` 限的是"已接受候选数"而非"已检查项数" → 一个含 5 万个"太新"文件的目录，上限完全不起作用 | 同上 |
| 4 | 页面内容比窗口高，**"执行清理"按钮初始在滚动视口之外**，UIA 的 `Invoke` 对它不生效 → 我的测试误判成"按钮点不动" | 端到端验证（读按钮坐标 Y=1453，而窗口只覆盖 160~880） |

### 4.1 两次"看起来像产品缺陷，其实是测试问题"

诚实记录，因为它们影响了结论的可信度：

- **测试假设错误**：`Backdate` 默认回拨 10 分钟，而规则默认 `MinimumAge` 是 1 小时 → 本该入选的项全被判成"太新"，12 个用例一起失败。生产行为是对的。
- **`File.SetLastWriteTimeUtc` 不能作用于目录**（Windows 不允许把目录当文件打开）→ 回拨目录时间戳必须用 `Directory.*`。
- **UIA 的两处不可靠**：`SelectionItemPattern.Select()` 不触发 RadioButton 的 `Click`；对不在滚动视口内的元素 `InvokePattern.Invoke()` 不真正触发 Click。因此主题切换验证改用真实鼠标点击、对话框检测改用 **Win32 `EnumWindows`**。

> 这条经验值得记住：**验证 UI 时，Win32 窗口层面的证据比 UIA 更可靠。** 进程实际有 10+ 个顶层窗口（`CiceroUIWndFrame`、`MSCTFIME UI`、`MediaContextNotificationWindow` 等隐藏辅助窗口），UIA 的 `FindAll(Children)` 看不到确认框**也不报错**，会直接得出"确认框没弹"的错误结论。

### 4.2 端到端验证的关键技巧

清理规则用 `Environment.ExpandEnvironmentVariables` 展开 `%TEMP%` / `%LOCALAPPDATA%`，因此**给子进程改这两个环境变量就能把规则目标重定向到受控沙箱**，从而在不碰用户任何真实文件的前提下跑完"扫描 → 确认 → 清理 → 撤销"整条破坏性链路。

## 五、已知限制

| 项 | 说明 |
| --- | --- |
| 回收站分支无自动化覆盖 | 避免污染用户真实回收站。做了带外勘察：`SHQueryRecycleBinW` 实测 HRESULT=0、`cbSize=24`（x64 对齐正确）、返回真实值 |
| 重解析点分支无测试 | 只在 `cmd /c mklink /J` 可用的环境下才能造 junction，无法保证不偶发失败，故未写 |
| 目录体积是近似值 | 扫描器对目录用深度受限的估算，界面展示够用 |
| `FreedBytes` 语义 | 是"成功处理项大小合计"，不是磁盘真实释放量（隔离区/回收站仍占盘），界面已按处置方式分档措辞 |
| 只读模式不实时刷新 | 设置页改动后需切页重载才更新本页提示条与按钮状态 |
| 提权真实动作 | 通道（结果文件 + token 校验）已验证，但**还没有任何真实的管理员动作**接入 |

## 六、复现方法

```powershell
# 一键跑完 7 项验收
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-all.ps1

# 只跑清理端到端（会用环境变量把目标重定向到受控沙箱，不碰真实文件）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ui-cleanup-e2e.ps1

# 出发布产物（含零依赖校验与体积报告）
powershell -NoProfile -ExecutionPolicy Bypass -File packaging\build-release.ps1
```

> ⚠️ 所有 `.ps1` 必须保留 UTF-8 BOM：Windows PowerShell 5.1 读**无 BOM** 的 UTF-8 脚本会按 GBK 解码，中文注释直接变成语法错误。
