# WinKit 技术选型（决策记录）

## 1. 结论

**C# + WPF + .NET Framework 4.8**，SDK 风格工程，`dotnet build` 构建，产出零依赖单文件 exe。

一句话理由：本项目约 80% 的工作是调用 Windows 系统 API，而分发要求是"免安装、单文件、秒开"——这两点正好是 .NET Framework 4.8 + WPF 的最强项，也是 Python + PySide6 的最弱项。

原方案 **Python 3.12 + PySide6 已废弃**。

## 3. 被排除的方案及原因

| 方案 | 排除原因 |
| --- | --- |
| **Python + PySide6**（原方案） | ①系统 API 全靠 fork PowerShell 桥接（占 20~30% 代码量）；②GIL，36 核用不上，全盘扫描慢 5~10 倍；③产物 60~90MB、冷启动慢、杀软误报重 |
| **Tauri (Rust)** | 本机无 Rust、**且 Windows 上必须 MSVC 链接器**（也未安装）→ 先装几 GB 工具链；Rust 编译迭代慢 |
| **Electron** | 本项目的功能几乎全是系统 API，正好全打在它的短板上；产物 200MB+、内存 300MB+ |
| **C++ / Qt** | 本机无 Qt、无 C++ 工具链；迭代速度最低 |
| **WinUI 3** | 需要 Windows App SDK 和复杂部署链；本机是 Win10 19045，Mica 等特性用不上 |
| **WinForms** | 分发与效率同样优秀，但**深色主题没有原生样式系统、要大量自绘**，与"深色/浅色主题"是 ★ 级需求冲突 |

## 4. 技术基线

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 运行时 | **.NET Framework 4.8** | Win10 1903+ / Win11 全部自带 → 目标机零安装 |
| UI 框架 | **WPF** | 样式系统能干净实现深色/浅色主题 |
| 目标框架 | `net48` 单目标 | 不做多目标，避免复杂度 |
| 工程风格 | SDK 风格 `csproj` | 已实测 `dotnet build` 可用 |
| 语言版本 | `<LangVersion>latest</LangVersion>` | 已实测接受；少数特性需 polyfill（见第 8 节） |
| **发布产物第三方依赖** | **零** | 系统能力全用框架自带程序集；NuGet 只用于测试工程 |
| DPI | PerMonitorV2（app.manifest） | 多显示器不同缩放不模糊 |
| 长路径 | longPathAware（app.manifest） | 已实测清单可用 |
| 权限 | `asInvoker`（app.manifest） | 默认标准权限，按需提权 |
| 并发 | `Task` + `async/await` + `CancellationToken`；重活用 `Parallel.ForEach` | 36 核可打满 |

## 5. 关键技术方案变化（相对原 Python 方案）

| 需求 | 原 Python 方案 | 现 C# 方案 | 收益 |
| --- | --- | --- | --- |
| 硬件信息 / SMART / 签名 | fork PowerShell + 解析 JSON + 编码归一化 | `System.Management`（WMI） | **整个桥接层删掉**，无子进程、无 300~800ms 开销 |
| 注册表 | `winreg` | `Microsoft.Win32.Registry` | 原生 |
| 进程 / 服务 | `psutil` | `System.Diagnostics.Process` + WMI | 原生 |
| 进程挂起 / 恢复 | `psutil.suspend()` | P/Invoke `NtSuspendProcess` | 少量 P/Invoke |
| 删除到回收站 | `send2trash` 或 ctypes | **`Microsoft.VisualBasic.FileIO.FileSystem`**（框架自带） | 零依赖实现，无需自己碰 `SHFileOperation` |
| 计划任务 / 磁盘健康 | PowerShell | `System.Management` + `schtasks` | 原生为主 |
| 权限提升 | `ShellExecuteW runas` | `ProcessStartInfo { Verb = "runas", UseShellExecute = true }` | 更规范 |
| 提权结果回传 | 临时文件 + token | **同左（本质限制不变）** | 仍需随机 token 文件 / 命名管道 |
| 并行扫描 | `multiprocessing`（spawn + Pickle 一堆坑） | `Parallel.ForEach` / PLINQ | **5~10 倍**，且代码更简单 |
| 实时图表 | QPainter 自绘 | WPF `Polyline` / `DrawingVisual` 自绘 | 同样零依赖 |
| 大数据表格 | `QTableView` + model | `DataGrid` + `VirtualizingStackPanel` | 虚拟化默认开启 |
| 主题 | QSS token | `ResourceDictionary` + `DynamicResource` | 切换更平滑 |
| 单实例 | `QLocalServer` | `Mutex` + `NamedPipeServerStream` | — |
| 打包 | PyInstaller（60~90MB） | `dotnet build` → 单 exe（**1~3MB**） | 体积降约 99%，秒开 |

## 6. 工程结构

```
windows-tools/
├─ WinKit.sln
├─ src/
│  ├─ WinKit.Core/          类库：无 UI、无平台调用，可纯单测
│  │                        Config / Journal（撤销） / Logging / Tasks / Rules
│  ├─ WinKit.Platform/      类库：系统访问
│  │                        Registry / Wmi / Native(P-Invoke) / Elevation / FileSystem
│  ├─ WinKit.App/           WPF 主程序（唯一引用 WPF 的工程）
│  │                        App.xaml / MainWindow.xaml
│  │                        Views / ViewModels / Controls / Themes / Assets
│  └─ WinKit.Tasks/         功能插件（每个模块一个文件夹 + 一个 TaskModule）
├─ tests/
│  ├─ WinKit.Core.Tests/    xUnit
│  └─ WinKit.Ui.Tests/      UI Automation（框架自带 UIAutomationClient）
├─ packaging/               发布脚本、版本号、图标、签名
└─ docs/
```

**分层纪律**：`WinKit.Core` 不允许引用 WPF，也不允许直接 P/Invoke → 核心逻辑可用毫秒级单测覆盖，也保住将来迁移 .NET 8 的退路。

**MVVM 不引第三方框架**：自己写约 100 行的 `ViewModelBase` + `RelayCommand`。原因：`CommunityToolkit.Mvvm` 是运行时库，会以 DLL 形式出现在输出目录，破坏"单 exe 零依赖"。若将来确实要引第三方，用 ILRepack 合并回单文件。

### 6.1 单文件的实现方式（M0 落地时确定）

`WinKit.App` **不** ProjectReference 另外两层，而是把它们的源码链接进来：

```xml
<Compile Include="..\WinKit.Core\**\*.cs" Exclude="...\obj\**;...\Compat\IsExternalInit.cs">
  <Link>LinkedSource\Core\%(RecursiveDir)%(Filename)%(Extension)</Link>
</Compile>
```

三条路里选它的原因：

| 方案 | 代价 |
| --- | --- |
| ILRepack / Costura.Fody | 需要联网安装构建期工具；版本漂移；对本项目"不联网、可复现"的定位是负担 |
| 自写 `AssemblyResolve` 从嵌入资源加载 | 运行时魔法；注册时机错了就在启动阶段崩，且极难排查 |
| **源码链接（选用）** | 唯一代价是 App 工程多编译约 30 个文件（构建仍是 3 秒），换来零外部工具、纯编译期、可复现 |

**分层纪律并未丢失**：`WinKit.Core` 工程依然独立存在且**没有** WPF 引用 —— 谁在 Core 里写 WPF 或 P/Invoke，Core 工程立刻编译失败；两个测试工程也依然引用独立程序集做单测。**注意**：`Compat\IsExternalInit.cs` 必须排除，否则与 App 自带的同名 polyfill 冲突（CS0101）。

## 7. 打包与分发

| 项 | 方案 |
| --- | --- |
| 产物 | `WinKit.exe`（单文件，可选同名 `.exe.config`） |
| 体积预期 | **实测 185 KB**（M0 全部三层代码编入单文件；原估 1~3 MB，实际小一个数量级） |
| 启动 | **秒开**（无自解压、无解压到临时目录的过程） |
| 构建命令 | `dotnet build -c Release` |
| 目标机依赖 | .NET Framework 4.8（Win10 1903+ / Win11 自带）；更老系统给明确提示 |
| 杀软误报风险 | **极低**——就是标准 .NET 程序，没有自解压、没有打包器壳 |
| 代码签名 | 可选，非必需 → **原决策点 D4（是否买证书）可以取消** |
| 交付形态 | 直接给一个 exe，不需要 SFX 自解压层 → **原决策点 D2 也取消** |
| 便携配置 | 写 exe 同目录，不可写则回退 `%LOCALAPPDATA%` |

## 9. 已知限制（诚实记录）

- .NET Framework 4.8 已进入"仅安全更新"阶段，不再有新功能（但随 Windows 生命周期长期支持）。
- WPF 是 net48 上的老版本，没有 .NET Core/5+ 的 WPF 渲染与 DPI 改进。
- 部分现代语言特性不可用（如默认接口实现）；`record`/`init` 需 polyfill。
- 少数高性能 API（`Span<T>`）需引入 `System.Memory` 包才完整，会破坏零依赖 → 默认不引。
- 不支持 Windows 7 / 8.1（不做兼容，启动时明确提示）。
- **长期退路**：若将来要迁到 .NET 8（自包含约 70MB，或框架依赖约 2MB 但目标机需装运行时），同一套 WPF 代码只需改 `TargetFramework` + 处理少量 API 差异，成本很低。
