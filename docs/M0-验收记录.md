# WinKit M0 验收记录

> 目的：留下**可复现的证据**，而不是"应该能跑"的结论。每条指标都注明用什么手段测出来的。

## 一、结论

**M0 骨架已完成并验证通过。** 一个免安装、单文件（185 KB）、零第三方依赖、双击即用的 WPF 程序，具备：主窗口导航、4 个可正常打开的功能页、深浅色主题、便携配置、日志、任务模型、撤销引擎。

## 三、验证手段与各自抓到的真实缺陷

这一节是本文档最重要的部分：**每种验证手段能查出什么、查不出什么**，以及它实际抓到了什么。

| 手段 | 能查出什么 | 实际发现 |
| --- | --- | --- |
| `dotnet build` | 语法、类型、XAML 编译期错误 | `ProcessPage.xaml` 一处 `Style` 被设置两次（MC3024）；契约缺口 2 个（`AsyncRelayCommand.RaiseCanExecuteChanged` 缺失、`Snapping` 是 WinUI API） |
| `check-xaml-resources.ps1` | **编译期查不出**的资源键拼写错误 | `SettingsPage.xaml` 引用未声明的 `StringMatch` 转换器键（打开设置页会白屏） |
| `check-conventions.ps1` | net48 不兼容语法、生产工程零依赖 | 拦截"注释里写了 `System.Text.Json`"的误报，证明规则能区分注释与代码 |
| 单元测试（139 个） | 逻辑正确性、边界、异常路径 | `UndoResult.Fail` 把"已撤销数量"吞掉了；日志重新初始化没清空环形缓冲 |
| `smoke-test.ps1` | 程序是否真的能启动、窗口是否真的构建出来 | 主窗口、数据目录、日志全部正常 |
| `ui-smoke-test.ps1`（UI Automation 点遍每页） | **页面级 XAML 运行时解析**、绑定转换器、DataTrigger | **致命缺陷**：`ProcessPage` 用了 `BasedOn="{DynamicResource ...}"`（`BasedOn` 是普通 CLR 属性，不支持动态资源）→ **整个进程页加载失败**。编译、静态检查、单测全都查不出来 |
| 真实鼠标点击（SendInput） | 交互链路是否真的接通 | 日志确认 `Dark → Light → Dark`，设置页主题切换有效；同时确认 UIA 的 `Select()` **不触发** `Click`，是自动化局限而非产品缺陷 |
| 受控实验（连续启动/杀灭 3 轮） | 单实例逻辑是否有缺陷 | 3 轮全部正常出窗口、零残留，并发第二实例被正确拦截 → **排除**了一个假缺陷 |

### 由缺陷反推新增的自动化规则

抓到 `BasedOn="{DynamicResource ...}"` 之后，立刻把这条规则加进了 `check-xaml-resources.ps1`，使其从"靠人踩坑"变成"机器自动拦截"。同理，`StringMatch` 事件催生了整个 XAML 资源键检查脚本。

**这些闸门现在都在持续生效**：`检查 BasedOn 用法，发现 0 处非法组合`。

### 两个只有"真正读数据"才会暴露的缺陷

**1. WMI 查询被重载劫持 → 所有 WMI 静默返回空集合（单元测试抓到）**

原实现在 `WmiQuery` 上同时有这两个重载：

```csharp
Query(string wql, params string[] properties)              // 想用的
Query(string wql, string scope, params string[] properties) // 命中的
```

`Query(wql, "Caption")` 这种「WQL + 属性名」调用会被重载决议选到第二个：属性名被当成**命名空间**，
`ManagementScope` 连不上 → 抛"无效命名空间" → 被 catch 吞掉 → **所有 WMI 查询都静默返回空集合**。
不抛异常、不报错，界面只是到处显示占位符"—"，非常容易被当成"这台机器读不到"。

修法：把带命名空间的重载改名为 `QueryInScope`，两种调用形态不可能再混淆。

**这个 bug 是 Platform 测试抓到的** —— 断言 `OsDisplay` 非空且不含"—"直接失败，才顺着查到根因。
如果只写"不抛异常"这种弱断言，它会一直潜伏下去。

**2. WPF 隐藏辅助窗口会干扰 UI 自动化判定**

进程有 2 个顶层窗口：主窗口 `1180x720`，以及一个 `134x27`、**名字为空**的隐藏辅助窗口。
早期版本的 UI 测试只看"顶层窗口数 > 1"就判为"弹出了异常对话框"，属于误报。
现在按"句柄不同 + 非离屏 + 尺寸 ≥ 40x40"过滤，误报消失。

### UI 层最终实测（最强的一条证据）

用 UI Automation 抓主窗口的完整元素树：**136 个元素，其中 77 个文本**。总览页显示的是真实数据而非占位符：

| 项 | 界面实际显示 |
| --- | --- |
| CPU | `Intel(R) Xeon(R) CPU E5-2686 v4 @ 2.30GHz 18 核 / 18 线程 / 2.3 GHz` |
| 操作系统 | `Microsoft Windows 10 专业版 (内部版本 19045.6456) 64 位` |
| 内存 | `16.6 GB / 63.9 GB`（使用率 25.9%） |
| 磁盘 | `C:\ (系统)  剩余 28.4 GB  已用 94.0 % · 共 476.6 GB` |
| 实时指标 | CPU `6.3 %`、网络 `↓ 1.3 KB/s ↑ 1.1 KB/s` |
| 导航分组 | `监控`（总览、进程管理）/ `系统`（撤销中心、设置） |

即 **WMI → Core → App → UI 全链路打通**，硬件信息、实时采样、主题、分组导航、磁盘列表都真实可用。

## 四、交付内容

### 工程结构

```
WinKit.sln
├─ src/WinKit.Core/       便携配置 / 日志 / 任务模型 / 撤销引擎 / 路径守卫（无 WPF、无 P/Invoke）
├─ src/WinKit.Platform/   P/Invoke 指标 / WMI / 注册表 / 提权 / 文件操作 / 撤销处理器
├─ src/WinKit.App/        WPF 主程序（Mvvm / Services / Views / ViewModels / Controls / Themes / Tasks）
├─ tests/WinKit.Core.Tests/      59 个用例
├─ tests/WinKit.Platform.Tests/  80 个用例
├─ scripts/               静态检查 + 冒烟测试 + UI 自动化测试
└─ packaging/             发布脚本（含零依赖校验与体积预算）
```

### 4 个功能模块（v0.1 范围）

| 模块 | 内容 | 状态 |
| --- | --- | --- |
| 总览 | 实时 CPU/内存/网络自绘折线图、系统信息卡、磁盘列表 | 可用 |
| 进程管理 | 进程表（排序/搜索/虚拟化）、结束进程的四道安全闸门、按需查命令行 | 可用 |
| 撤销中心 | 按批次查看操作日志、倒序回滚、只读模式拦截 | 可用 |
| 设置 | 主题三选、只读审计模式、采样间隔、数据目录与日志位置 | 可用 |

### 关键技术决策

1. **单文件靠源码链接，不靠打包器**：`WinKit.App` 不 ProjectReference 另外两层，而是用 `<Compile Include="..\WinKit.Core\**\*.cs">` 把源码直接编进 `WinKit.exe`。理由：ILRepack / Costura 都要联网装构建期工具，而自写 `AssemblyResolve` 是运行时魔法（启动失败极难排查）。源码链接是纯编译期的、零外部工具、可复现的。
   **分层纪律没有丢失**：`WinKit.Core` 工程依然独立存在且没有 WPF 引用，谁在 Core 里写 WPF，Core 工程就编译不过；两个测试工程也依然引用独立程序集。
2. **热路径 P/Invoke，冷路径 WMI**：每秒采样走 `GetSystemTimes` / `GlobalMemoryStatusEx`（微秒级，可在 UI 线程直接调）；硬件信息走 WMI（单次 50~300ms，必须后台线程 + 10 分钟 TTL 缓存）。
3. **插件用反射自动发现**：新增功能页不需要改主窗口代码 —— 这既降低了耦合，也是本次能 5 个 agent 并行开发同一工程的前提。
4. **零第三方依赖是不可妥协的**：发布产物里没有任何 DLL，由打包脚本强制校验。

## 五、已知限制与遗留问题（诚实记录）

| 项 | 说明 | 计划 |
| --- | --- | --- |
| 结束进程的 PID 复用竞态 | 二次确认框弹出期间目标进程可能退出且 PID 被回收，理论上会误杀新进程 | M2 加 StartTime 二次比对 |
| 操作日志 `Size` 字段语义借位 | "结束进程"没有磁盘影响，代码里填了内存字节数 | M2 明确字段语义或拆字段 |
| 采样间隔上限不一致 | VM 允许到 10000ms，设置页 Slider 上限 5000ms，手改配置会被写回 5000 | M2 统一 |
| 命令行读不到时无法区分原因 | WMI 返回 null 时，分不清"真没有命令行"与"权限不足" | M2 改 `WmiQuery` 返回错误码 |
| 高 DPI / 多显示器 | `PerMonitorV2` 清单已加，但未在真实双屏环境验证 | 有环境时补 |
| Ctrl+K 搜索过滤 | 只做了代码审查，未做 UIA 输入测试 | M2 补自动化 |
| 温度 / SMART | 尚未实现；且部分机器根本读不到 | M5，且会明确标注"尽力而为" |
| 提权任务通道 | 管道已打通（结果文件 + token 校验已验证），但**还没有任何真实的管理员动作** | M3 随 hosts / 环境变量功能落地 |

## 六、复现验证的方法

```powershell
# 1. 静态检查（编译前就能拦住资源键与非法用法）
powershell -File scripts\check-xaml-resources.ps1
powershell -File scripts\check-conventions.ps1

# 2. 全部单元测试
powershell -File scripts\test-all.ps1

# 3. 出发布产物（含零依赖校验 + 体积报告）
powershell -File packaging\build-release.ps1

# 4. 启动冒烟测试（进程存活 / 窗口标题 / 数据目录 / 日志）
powershell -File scripts\smoke-test.ps1

# 5. UI 自动化测试（真的点开每一个导航页，检查日志有无异常）
powershell -File scripts\ui-smoke-test.ps1
```

> 注意：Windows PowerShell 5.1 读**无 BOM** 的 UTF-8 脚本会按 GBK 解码导致中文注释变成语法错误。本仓库所有 `.ps1` 都带 UTF-8 BOM，不要用不带 BOM 的方式重写它们。
